# Native execution and optional qualification

## Ordinary Codex schema2 execution

For a new ordinary Codex schema2 assignment, use `sprint-create`, then
`sprint-send` on its exact acknowledged chat. Historical qualification files,
recipes, linkage reviews and synthetic same-chat bootstrap are not prerequisites.
Optional supplied `qualification` and `qualification_sha256` must form a valid
path/digest pair; the ordinary route does not open these diagnostic files.
Current runtime/protocol, provider/model/effort, effective configuration, actual
permissions/approval/network, integrations and in-operation seals still apply.
Readiness remains tool-free and is not evidence that file tools work. Report
capability from the actual task and independently observed file results.

Reject unresolved intents or ACKs before any resume or mutation. Existing
qualification journals (including qualification state, receipts, recipes and
accepted bootstrap) remain with their original owner and evidence; never adopt,
erase or relabel them as ordinary sessions. Use a genuinely new owned assignment
without replaying earlier work. Selected identity, terminal prior turn, persistence,
operation receipts and owned cleanup remain binding. Changes between completed
operations do not themselves require historical requalification; active-operation
changes stop execution, and incompatible existing session bindings require explicit
reconciliation rather than migration.

The remaining qualification procedure is an optional, separately authorized
diagnostic workflow for schema2. Its evidence requirements apply to that workflow,
not ordinary execution. Schema1 and Claude retain their existing evidence rules.
Trusted callers establish provenance; JSON records grant no authority. Synthetic
peers establish software behavior only, never native host qualification.

## Actual context and control integrity

The original schema 1 retains its bounded profiles, physical control exclusion,
network-disabled contract and positive/denied-read proof. Schema 2 records actual
Codex grants. Its exact context fields are schema, writable_roots, temp_roots,
protected_names, read_roots, deny_read_paths, network, approval and task_permissions.
Root lists retain complete actual grants. Empty protected/denied lists are valid.
The schema-2 grant descriptor is exactly
`{extends: ":danger-full-access", network: {enabled: BOOLEAN}}`; the boolean must
match network=enabled or disabled. This descriptor records trusted actual grants;
it is not a native named-profile definition. The implemented direct-builtin bridge
supports network=enabled only. A consistent network-disabled descriptor remains
valid context but this bridge rejects it before allocation/native effects, until a
faithful mapping is implemented and evidenced. Filesystem overlays and other actual
shapes likewise fail before effects. Never translate a non-full parent into full
access or invent restrictions absent from its grants.

Approval records contain system=codex, the actual policy (never, on-request,
on-failure or untrusted), and reviewer (user, auto_review or null). A policy that
uses approval needs its supported reviewer and actual host bridge. Under never,
a null reviewer is valid; an incidental runtime default is recorded separately
from the requested reviewer and is not an authorization mismatch. No artificial
parent attestation or permissive approval answer is supplied.

Schema 2 uses the SAME exact native builtin reference `:danger-full-access` in
initialization, task execution and local probes. Its canonical profile mapping is
`{init: ":danger-full-access", task: ":danger-full-access"}`; schema 1 retains
its generated named definitions. Startup emits the explicit CLI selector
`permission_profile=":danger-full-access"`, with no generated schema-2 permissions
or default_permissions alias. Incompatible task-local initialization/execution
aliases must be removed or replaced with that exact builtin only after existing
owners and unknown operations are reconciled. Effective config selectors may be
null/omitted on the reviewed runtime; contradictory returned selectors fail closed.
Unselected user profile declarations may remain. Builtin catalog admission and
metadata do not qualify file tools; returned active permission identity, actual
approval and roots remain checked. Profile references, context and source/runtime
bytes bind every probe, linkage and same-chat proof; old alias proofs do not admit
this representation. Readiness authorizes only a harmless answer;
observed initializer tool activity stops dispatch while retaining its acknowledged
turn. This detects unauthorized action; it does not suppress the tool catalog or
claim preventive filesystem isolation.

Under full access, control/runtime/config paths can be writable. The internal
integrity_only roots retain every actual root; controls must have ordinary,
non-aliased paths and frozen canonical bytes. Kernel journal ownership and source
seals remain required. These are integrity checks, not filesystem exclusion or a
guarantee against a malicious fully authorized process. Context schema, roots,
profiles, actual approval and network all bind the proof; changing them invalidates
qualification. The legacy text envelope is unchanged. Built-in text dispatch and
its uncertainty consumer explicitly opt into this actual schema2 parser without
tools; they use the same integrity-only path checks and frozen control/source
references. This opt-in does not change native tools=True validation or admit
schema2 to native tools=False callers. A consistent network-disabled text context
remains valid data; it never overrides a host network restriction or changes the
native builtin bridge's supported network mapping.

## Establish the selected host boundary

Pin the selected executable, protocol, platform, native home, effective executable
copies and each helper actually used. Record independent release/build and handler
source correspondence for shell and native patch families. A version string,
profile declaration, publisher signature alone, tools:true or marker chat is not
file-tool qualification. Keep unqualified integrations disabled.

`effective_native_executables` contains {path,sha256} per role. All phases determine
helper requirements: schema 1 on Windows uses main, runner and setup and needs the
actual elevated-sandbox readiness check. Schema 2 full access uses no Windows
sandbox in any phase, requires main plus the bound probe interpreter, and neither
requires runner/setup nor invokes sandbox readiness. Linux uses main plus the
probe interpreter. Genuine runtime/protocol and kernel-cleanup limits still apply;
software tests on another OS do not establish Windows support. Never install or
elevate an unused sandbox. Native auth dependencies remain pinned without exposing
credentials. Only the reviewed runtime version is admitted; new versions need real
compatibility evidence, not edited version literals.

## Local probe and versioned recipes

`native-probe --workdir ... --parent-context ...` calls no model. The paired optional
`--linkage-file` and `--linkage-sha256` produce complete prerequisite evidence for
the exact final binding. A diagnostic receipt cannot replace that evidence.
Configuration, profiles, effective executable pins and owned cleanup are checked.

Schema 1 retains two exact noncredential fixtures, positive reads and explicit
PermissionError sentinels under both profiles. On Windows its sandbox must already
be legitimately ready. A new native home is not separate OS-account isolation;
coordinate any real sandbox setup under actual host ownership. Never transplant
encrypted account state or disrupt another session as a diagnostic.

Schema 2 creates ONE exact synthetic fixture in the final authorized work root,
with an ASCII marker and one LF byte. Local command probes successfully read it
under both actual profiles; there is no denied fixture or negative-read claim.
The complete probe has schema=2 and filesystem_isolation=false. Its checks bind
stage/case, exact profile, target, bundled command digest, exit code 0 and the
native-positive-read sentinel. Exact fixture path, identity and bytes remain frozen.
Schema 1 uses schema=1 and its original four checks.

## Synthetic session and same-chat admission

`native-qualify --workdir ... --sprint ... --parent ... --authorization-file ...
--parent-context ... --local-probe-receipt ...` selects the configured main external
executor. It accepts no arbitrary brief, RPC, program, fallback or policy override.
Actual provider authorization, independently accepted linkage and local probe,
and separate scoped top consent when applicable precede inference.

The engine locks the real journal, allocates one chat, saves its ACK immediately,
checks identity and completes readiness without tools. It reconnects to the SAME
ID and verifies the public readiness digest. Schema 1 retains its allowed/denied
cases under both profiles. Schema 2 then executes exactly ONE task shell-read and
ONE task native real edit, in that order, against the single allowed fixture.
Fresh schema-2 patch linkage must select
`native-real-edit-restore-verification-v1`. The patch changes the original ASCII
marker plus LF (A) to that marker plus `:written` and LF (B), in place. Exactly one
canonical native fileChange must report completed and the exact absolute path;
its original ordered typed item/hash remains unchanged. A completed no-op, prose,
wrong bytes/path/identity, extra tools or malformed status cannot qualify access.
Readiness, read and patch remain three model turns; connection three reads persisted
items only. No model restoration turn is requested.

Before the patch the engine holds a checked regular-file descriptor, original
bytes, device/inode and mode. A local phase permits A/B only during the owned patch
callback through postguard and close. It requires exact B for patch success.
The previous connection's cleanup is invalidated before connection two. Only
current owning close with verified empty kernel cleanup permits local restoration.
Restoration checks the held descriptor and lexical/canonical path, rejects symlinks,
changed identity/mode and unexpected bounded bytes, then writes A fully in place,
truncates, fsyncs and verifies A/identity/mode. Short writes are completed. There is
no chmod, ACL change, path replacement, recovery on restart or extra RPC while B
remains. A failed patch that wrote B can be safely restored after cleanup while its
original error/unknown operation remains failed. Unknown cleanup leaves B untouched.
Original errors are preserved; close/restoration/publication failures block success
and retain bounded error categories where storage remains available. Exact guards
cannot provide isolation against same-user races under full access. POSIX mode
checks do not establish Windows DACL behavior; native Windows QA is separate.

For schema-2 shell evidence, the native command display represents the complete
argv. Decode only that bounded outer POSIX quoting with comments disabled, without
execution or inner-script normalization. It must equal the exact bound Python,
-I, -c, original model-read code and fixture path, or one source-backed shell wrapper
whose script token equals the exact planned command. Supported wrappers require an
absolute existing executable file: bash/zsh/sh with -c or -lc on Linux;
powershell/pwsh (including .exe) with optional -NoProfile then -Command, or cmd
(including .exe) with /c on Windows. Reject extra arguments, unknown names/flags,
encoded commands, env/exec prefixes and altered scripts. Keep planned command,
request and instruction bytes unchanged, exact cwd/exit/sentinel checks and raw
ordered native item hashes for persistence. Schema 1 retains its historical string
equality; decoding source/software cases does not qualify Windows or native tools.

After reconnect the selected driver exhausts the exact acknowledged turn and
compares the complete ordered typed tool inventory and hashes for exact equality.
Schema 2 patch retains one fileChange identity/hash. Schema 1 retains its historical
correlated fileChange/functionCallOutput pair and both hashes. External standalone
functionCallOutput input is distinct from canonical native patch evidence; it cannot
supply schema-2 patch proof. The generic history reader still preserves supported
legacy correlated items without silently dropping unexpected qualification items.
Only agentMessage, userMessage, reasoning and plan may be ignored in that inventory.
Unknown families, extra/missing/changed items or partial history fail. Reasoning and
unrelated history are not retained as proof. The driver separately validates only
the closed connection-scoped configWarning, remoteControl/status/changed and
account/rateLimits/updated notices before thread checks. The rate-limit notice has
exactly rateLimits with a closed typed snapshot: source Option fields may be omitted/null,
integer fields retain signed i32/i64 bounds, unknown plan strings remain valid and
the reached-type enum stays closed. Snapshot strings/balances are not parsed or
retained and never authorize payments, dispatch or model changes; no quota/budget
state, RPC/refetch or progress timer changes. Warning summary/details and optional typed path/range,
and the exact remote status/identifier fields, are discarded without persistence.
They are neither progress nor tool/permission evidence and never reset silence or
cancellation state. Malformed notices and unknown/unscoped/foreign tool events still
fail closed. Own-thread warning requires exactly threadId/message; thread/goal/cleared
requires exactly threadId. These notices are discarded after the original thread
identity guard, without treating warning text as benign, clearing workflow goals or
resetting progress. Global/null-scope warnings and unobserved queue/goal events
remain rejected. At the three generic turn rejection sites, only the first bounded
eight-field record is retained: unchanged error code, canonical-JSON method digest,
closed params type/count and four scope-presence/match booleans. No raw method,
foreign ID, keys or payload are retained; original legitimate own ACKs remain.
See [history reading](host-codex.md#bounded-history-reading).

Immutable observations end awaiting_independent_acceptance; they do not accept
themselves or deliver a brief. Schema 2 records filesystem_isolation=false. An
independent reviewer accepts the exact evidence, and qualification references its
pinned bootstrap={receipt,acceptance}. These records belong to the explicit
diagnostic workflow; ordinary create/send rejects such a journal rather than
adopting it. Diagnostic validation checks the selected binding, host/root/sprint/
parent/thread, acknowledged qualification turns, immutable results and cleanup.
Chat A's diagnostic evidence cannot describe chat B. Schema1 preserves its
historical evidence-backed create route. Backend persistence and GUI visibility are
separate observations. Unknown ACKs remain unknown and are never replayed.

## Protected evidence schemas

References are {path,sha256}, using configuration anchors. All files are frozen
and rechecked before effects. Linkage contains schema, kind=native-tool-linkage,
author, exact binding, release={identity,runtime_sha256,native_helpers,source} and
inventory. Source and handler_source reference bounded JSON evidence records.
Inventory entries contain family, item_type, boundary, profiles_sha256,
handler_source and cases. Schema 1 retains
boundary=same-generated-native-filesystem-permissions and its four cases per
family. Schema 2 uses boundary=same-actual-native-permissions-v2,
filesystem_isolation=false, and only task_allowed for each shell/patch family.
Cases use the bundled versioned recipe and bounded native assertions, independently
reviewed against actual handler source. Schema-2 patch task_allowed requires the
recipe `native-real-edit-restore-verification-v1` and static assertion
{item: operation, path: [status], equals: completed}, with no output
assertions. It can be frozen before the probe allocates its random fixture; planned
path/token and instruction digests bind afterward. Schema-1 paired-output/denial
assertions and schema-2 shell assertions retain their existing semantics.

The complete local probe contains schema, kind=native-local-probe, author, binding,
root={lexical,canonical}, attempt, profile_names={init,task}, fixtures, checks,
cleanup, inference_started=false and linkage. Schema 2 adds filesystem_isolation=false.
Independent acceptance remains schema=1, kind=independent-native-acceptance,
decision=accept, reviewer, distinct author, artifact_sha256, binding_sha256 and
source. It lives separately from its accepted artifact to avoid circular hashes.

Human qualification scope remains schema_version=1, trusted source, authorizations
and qualification_reviews={probe,linkage}. A native-qualification authorization
binds operation=qualify, stable host, canonical workdir, sprint_id, parent_chat_id,
profile, provider, binding_sha256, local_probe_sha256, linkage_sha256 and
instruction_sha256. The instruction hash covers exact readiness and deterministic
synthetic requests including the new patch recipe; a previous no-op instruction
grant cannot authorize this edit. New module hashes require fresh linkage/probe/
authorization/qualification, without rewriting original evidence. No arbitrary
task text is admitted.

The accepted qualification record uses schema=2 and filesystem_isolation=false for
actual rights. Required checks are protocol, identity, persistence, no_replay,
ownership, tool_environment, task_read_shell, task_write_patch and actual_permissions.
The latter binds effective profiles, actual approval and returned roots; it does
not claim every filesystem path was tested. Typed check receipts use the matching
schema and exact binding. Each successful file-tool check includes one tool-channel
record whose data is the exact closed observation summary from the same-chat
bootstrap (turn_id, type, stage, case, target, native_items and status). A marker-only
journal record cannot prove tool access. Schema 1 keeps its deny-read/root_confinement checks.
Empty models/checks, software tests and pending evidence cannot qualify real tools.

New schema-2 qualified documents, journals and receipts carry the matching overall
recipe `actual-real-edit-restore-v1`; task_write_patch expects
`successful-native-real-edit-restored-patch-v1`. Before success the journal stores
`qualification_restoration`, copied exactly to receipt `restoration`: recipe,
fixture lexical/canonical/device/inode/mode, original/written/restored hashes,
patch operation, original ACK and native observation, owning connection marker
and cleanup, outcome and safe secondary-error categories. Outcomes are restored,
failed, notneeded or cleanupunknown; only restored with no errors qualifies.
Every bootstrap validation checks the exact receipt/journal proof, original patch
ACK/result and restored fixture. Removing/swapping recipe marks cannot downgrade
new evidence. Existing history is rejected before qualification identity updates;
no later invocation restores, reallocates or replays it. Historical schema-2 no-op
bootstrap/parser evidence stays valid under its original pinned bundle and binding;
it grants no continuation under changed module pins. Schema 1 keeps its recipe.

Offline regression controls distinguish substitution from OS exclusion while the
checked descriptor remains open. The permissions negative control clears the
actual owner-write/read-only bit and verifies a real stat transition; it does not
assume that 0600 versus 0644 changes Windows permissions. If Windows prevents inode
or symlink replacement with that descriptor held, tests assert the observed
PermissionError, retained original identity, safe restoration and no continuation.
Successful substitution must instead be detected without overwriting it. The
symlink-specific case first probes actual symlink-creation capability and records
a precise capability skip only for observed unsupported/privilege errors; other
negative controls still execute. These software controls do not qualify DACLs.
A successful patch that has returned to A during owning close is rejected before
connection three or receipt publication; notneeded remains valid only on an
already-failed patch, whose original error/intent/ACK are preserved.
